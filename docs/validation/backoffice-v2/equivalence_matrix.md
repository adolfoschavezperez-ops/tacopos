# Matriz de Equivalencia Funcional Definitiva — Backoffice 1.0 vs. Backoffice 2.0 (Fase 5.1)

Auditoría y cierre de paridad funcional realizados mediante inspección directa del código fuente de Backoffice 1.0 (`lib/screens/admin/`, `lib/core/`, `lib/services/taco_pos_repository.dart`) y Backoffice 2.0 (`lib/backoffice_v2/`), sin acceso a producción.

**Estados utilizados:** `Pendiente` · `Implementada parcialmente` · `Implementada` · `Validada funcionalmente` · `Bloqueada por dependencia` · `Equivalencia completa`

## 2. Esquema aditivo implementado en DEV para Metas y Presupuestos (Fase 6)

- **Colecciones DEV** (aisladas por `restaurantId` y `branchId`, sin impacto en POS Android ni producción):
  - `restaurants/{restaurantId}/backofficePurchaseTargets/{branchId}_{categoryKey}`: `{ restaurantId, branchId, category, targetPer100Sales, updatedAt, updatedByEmployeeId, updatedByEmployeeName }`.
  - `restaurants/{restaurantId}/backofficePurchaseBudgets/{branchId}_{purchaseItemId}`: `{ restaurantId, branchId, purchaseItemId, itemName, unit, targetWeeklyQty, updatedAt, updatedByEmployeeId, updatedByEmployeeName }`.
  - `restaurants/{restaurantId}/backofficeFinanceBudgets/{branchId}_{budgetType}`: `{ restaurantId, branchId, budgetType, amount, periodLabel, updatedAt, updatedByEmployeeId, updatedByEmployeeName }`.
- **Seguridad**: lectura para `canReadFinance(restaurantId) || canReadPurchases(restaurantId)` con `canAccessBranch`; escritura exclusiva para `canManageSuppliersCatalog(restaurantId) && canAccessBranch(restaurantId, request.resource.data.branchId)`.
- **Compatibilidad**: 100% aditivo; Android ignora estas colecciones y nunca bloquea ventas.
